# Question bank

Likely questions, with answers you can give in about 30 seconds. Grouped by topic; new steps add to it.

---

## Architecture

**Q: Walk me through the system.**
FE → API gateway → Redis Streams → two worker services (index, deep dive) → Postgres. Both flows are async: POST returns 202 and the work happens in workers. Code is never stored. Workers clone at a pinned commit into a temp dir and delete it afterwards.

**Q: Why two worker services instead of one?**
Different lifecycles and scaling profiles. Indexing is long, heavy and rare (once per repo). Deep dives are shorter, frequent, and will grow into multi-step workflows. Separate services scale, deploy and fail independently.

**Q: Why REST and not GraphQL?**
One client that I own, and immutable, cacheable snapshots (pinned commits). GraphQL pays off with many clients that have different data needs. Here it would add a schema layer and make HTTP caching harder for no gain.

## Data model

**Q: Why is the database schema generated from Python classes?**
One source of truth. The SQLModel class is the table, the API schema and the validation. Alembic autogenerates the migration as a diff between the models and the database, I review it, and `alembic check` in CI catches drift. Hand-written DDL plus separate DTOs means three copies that drift.

**Q: What can go wrong with autogenerated migrations?**
It's a diff, not intent. A rename looks like drop + add, which loses data. Enum and CHECK changes are poorly detected, and data backfills are never generated. So every migration is reviewed like code, and destructive changes follow expand → migrate → contract.

**Q: How do you store the tree? Why not a closure table or `ltree`?**
As `contains` edge rows (an adjacency list kept in the edges table), with a partial unique index so a node has at most one parent. "Expand a node" is one indexed join on `edges.source_id`. Trees are rebuilt, never moved, so the strengths of materialized paths and closure tables (subtree reads, moves) aren't needed. If whole-subtree reads become common, a recursive CTE works, and `ltree` is the upgrade path.

**Q: Why is the tree stored as edges instead of a `parent_id` column?**
One relationship table for every link between areas, and `/map` returns `{nodes, edges}`, the shape canvas libraries like React Flow take. The one-parent guarantee survives as a partial unique index on `target_id WHERE kind = 'contains'`. The cost is query convenience: children become a join and "top level" an anti-join. Cycles aren't the difference: a `parent_id` column allows `A.parent = B, B.parent = A` just as edges do. v1 has none because only the indexer writes the tree, top-down, in one transaction, and the tree is immutable; re-indexing will build a new versioned tree rather than edit one in place.

**Q: How do you guarantee one repo per URL?**
Two layers. The gateway's Redis dedup marker (`SET NX`) stops duplicate jobs. Postgres `UNIQUE (url)` plus an `ON CONFLICT` upsert in the worker is the final guard, even if two workers race. Both depend on the URL being normalized first (lowercase host, no `.git`, no trailing slash).

**Q: What stops a node from having two parents? And what doesn't stop a cycle?**
A partial unique index on `edges(target_id) WHERE kind = 'contains'`: a node can be the target of at most one `contains` edge. It does not prevent cycles (`A contains B contains A`), and neither would a `parent_id` column. Cycles can't happen in v1 because only the indexer writes the tree, top-down from its own recursion, in one transaction, and the tree is never edited afterwards.

**Q: Repos can be re-indexed. How is the tree still safe?**
Versioned snapshots: a re-index builds a new, immutable tree for the new commit in one transaction, and the repo points at its current snapshot. The "built once, never edited" argument holds again per snapshot, and deep dives keep pointing at the snapshot they were made from, which gives staleness detection almost for free. Editing the tree in place would need a cycle check on every edge insert (a recursive CTE or a trigger).

**Q: Why store a node's paths as an array column and not a files table?**
Paths are folder prefixes or files, always read and written with their node, and handed as-is to the deep dive's sparse checkout. Areas may overlap and there's no "each file exactly once" rule, so a join table would enforce nothing. `CHECK (cardinality(paths) > 0)` keeps the one rule that matters: an area with no paths would give a deep dive nothing to check out. If "which area covers file X?" becomes a query, a GIN index on the array handles it.

**Q: Why no `depth` column?**
It's derivable from the tree, and a stored copy can disagree with the real structure. It existed only to fetch "the top 2 levels"; once `/map` returns the whole tree, nothing reads it.

**Q: Why did you add a CHECK constraint to a generated migration by hand?**
Alembic's autogenerate doesn't detect CHECK constraints (or server-default changes). Generated migrations are a starting point that gets reviewed; adding what the diff can't see is part of that review, and the comment in the migration says so.

**Q: Why store `status` as VARCHAR rather than a Postgres enum?**
Adding a value to a native enum needs `ALTER TYPE`, which autogenerate doesn't detect, and there are transaction caveats. VARCHAR plus Pydantic validation avoids that. Honest trade-off: right now the database itself doesn't reject a bad value; a CHECK constraint closes that gap.

## Redis

**Q: Redis is in-memory. What happens if it crashes?**
AOF with `appendfsync everysec`: every write is logged and fsynced once per second, so a crash loses at most about 1 s. Postgres is the source of truth. At worst a just-accepted job is lost and the client re-adds the repo (POST is idempotent).

**Q: Why `noeviction`?**
Under memory pressure the other policies silently drop keys. For a queue, that's a lost job or a broken dedup marker. `noeviction` makes writes fail loudly instead, so the gateway returns 5xx and the client retries. Cache keys, if they ever share this Redis, get TTLs plus `volatile-lru`, or better, their own instance.

**Q: How do you make "dedup + enqueue" atomic in Redis?**
One Lua script: `SET NX` the marker, and only if that succeeded, `XADD` the job. Redis executes a script atomically (single-threaded), so there's no state where the marker exists without the job.

**Q: Tell me about a bug you found in this project.**
The workers wait for jobs with `XREADGROUP BLOCK 5000`, and redis-py 8 changed its default socket timeout from none to 5 s. Each time the queue sat empty, the client gave up on the socket right as Redis was about to answer "nothing new". It raised `TimeoutError` and crashed the worker. Unit tests missed it because they block for 1-10 ms; a crash test against a real worker caught it as soon as the queue went idle. The fix is an explicit `socket_timeout` (15 s) in `app/config.py`, and a test that asserts it's longer than every worker's blocking read, so the two numbers can't drift apart again. The lesson: a blocking command needs a client timeout longer than the block, and a library default that matters belongs in your config, not in the library.

**Q: Why not just catch the timeout and loop?**
That would hide a misconfiguration. A timeout shorter than the block means every idle read fails and reconnects, and a real network hang looks just like a normal empty read. The timeout should only fire when Redis is actually unreachable.

## Gateway / idempotency

**Q: What happens if a user POSTs the same repo twice? Or a proxy retries?**
Both get 202 and nothing new happens. The URL is normalized first, then a Lua script does `SET NX` on a dedup key and `XADD`s the job only if the key was new. Same input, same result, so it's idempotent.

**Q: Why doesn't POST return the repo id?**
The gateway writes only to Redis. Returning an id means inserting a Postgres row in the request too, which is a dual write: a crash between the two leaves them inconsistent. The worker creates the row (an upsert on the unique URL), and the client sees it in `GET /repos` once indexed.

**Q: Why Lua and not MULTI/EXEC?**
MULTI/EXEC queues commands blindly; it can't say "XADD only if SET NX succeeded". Lua can branch, and Redis runs the whole script atomically. Without atomicity, a crash between the two calls leaves a marker with no job, and the repo can never be re-added.

**Q: Why 202 and not 201?**
201 means "created", but nothing is created yet, only queued. 202 means "accepted for processing", the standard answer for async work.

**Q: The user sends a URL and your server runs `git clone` on it. What could go wrong?**
Three attacks. `file://` or `ssh://` clones local or internal things, which https-only blocks. A string like `--upload-pack=cmd` is parsed by git as an option (command injection); we only accept a strict URL shape, and the worker will put `--` before the URL. SSRF: `https://internal-host/` or `169.254.169.254` (cloud metadata), blocked by a host allowlist. Rule: reject unusual input, never repair it.

**Q: The queue payload came from your own gateway. Why validate it again in the worker?**
Anything that crosses a process boundary is untrusted: old message versions, a bug in another producer, a manual `XADD`. It costs nothing because it's the same class, `RepoCreate`.

**Q: What if Redis is down?**
The script never ran, so nothing was written. The gateway returns 503 and the client retries safely. No partial state is possible.

## Local dev / ops

**Q: Why Docker Compose for dev?**
Same engines as production (no SQLite drift), one command to start, and healthchecks so tooling waits until the services are actually ready. It's not a production orchestrator; production would be Kubernetes or ECS with managed Postgres and Redis.

**Q: How do you run migrations in production?**
As one release step before the new code rolls out, not on app startup in every replica (two replicas would race on `upgrade`). Destructive changes use expand → migrate → contract so old and new code both work during the rollout.

## Index worker

**Q: How does the worker run `git clone` on a user's URL safely?**
Three layers. First, the gateway only accepts https URLs from allowed hosts. Second, the clone puts `--` before the URL, so a value starting with `-` can't become a git option. Third, git runs with a timeout, `GIT_TERMINAL_PROMPT=0` (a private repo fails right away instead of waiting for a password), and no system or global config, so `url.insteadOf` or credential helpers on the host can't change what gets fetched.

**Q: What happens if the worker crashes in the middle of a job?**
The job stays in the consumer group's pending list, because `XREADGROUP` doesn't delete it and only `XACK` does. We ack only after the database commit, so a crash loses nothing. The heartbeat stops with the process, so once the job has been idle for a lease (60 s), another worker's loop claims it with `XAUTOCLAIM` and runs it again.

**Q: What if the same job gets processed twice?**
Delivery is at-least-once: the worker can commit and then crash before acking. So the worker first checks whether the repo already has a SHA, and if it does, it acks without cloning. If two workers race on the same job, `INSERT … ON CONFLICT (url) DO NOTHING` keeps the first SHA.

**Q: Why doesn't a failed job get acked?**
Acking a failure throws the job away, and the dedup marker would then block re-adding the repo. So a failed job is left pending, and the reaper retries it after one lease. On its 4th delivery it goes to the dead-letter stream and its marker is freed (see Reliability).

**Q: Why `git ls-files` instead of walking the folder?**
Git already knows the real file set: tracked files only, no `.git/`, no untracked or ignored files, always `/` separators. It's also the same source the deep dive's sparse checkout uses, so paths match exactly. `-z` makes git return names with spaces, quotes or non-ASCII verbatim instead of quoting and octal-escaping them.

**Q: How do the repo row and its tree stay consistent?**
They're written in one transaction. The repo row is inserted with `ON CONFLICT (url) DO NOTHING RETURNING id`; if no id comes back, another worker won the race, so this one rolls back instead of saving a duplicate tree. A repo is never visible as indexed with a missing or half-saved tree.

## LLM gateway

**Q: Why does the gateway contract carry messages, tool definitions and a response schema instead of just text?**
Both the indexer and deep dives are agents, and an agent needs structured tool calls: the model returns `{id, name, arguments}`, not prose. A text-only contract would also force parsing JSON out of free text instead of using native structured output (`response_schema`).

**Q: Why put the contract's Pydantic models in one shared package?**
The client and the gateway import the same classes, so the two sides can't drift. It's the same "two copies drift" rule as the rest of the schema-driven design, applied across a service boundary.

**Q: Who validates the arguments of a tool call?**
Each tool, with its own argument model. The contract only guarantees that `arguments` is valid JSON (`JsonValue`, not `Any`); it doesn't know which tools exist.

**Q: What happens when the model stops on `max_tokens` or refuses?**
The answer is incomplete or unusable, so it's never treated as final: `from_contract` raises `GatewayAnswerError`. In the indexer that makes the node fall back.

**Q: Why is a bad answer handled differently from an HTTP error?**
A bad answer is local: one node falls back to directory grouping and the rest of the tree is kept. An unreachable gateway is global: failing over every node would produce a tree that's fallback everywhere. So HTTP errors fail the job, and the queue retries it later.

**Q: Why an adapter between LangChain messages and the contract?**
The gateway is its own service with its own contract; it shouldn't depend on a client library's classes. `to_contract` and `from_contract` are the only code that knows both, so a change on either side touches one place.

**Q: Why must a tool call id never be missing?**
A model can ask for several tools in one turn, and each result is matched to its call by id. A missing or mixed-up id means the model reads one tool's result as another's.

**Q: Why a separate gateway service instead of calling Anthropic from the workers?**
One place holds the API key, picks provider and model, retries, caches prompts and handles refusals; workers know only the contract. Swapping provider or adding rate limiting touches one service. The key reaches only that container (one variable from `.env`, never baked into the image).

**Q: Your contract drops thinking blocks. Is that safe?**
Yes for correctness: removing *all* thinking blocks keeps a conversation valid; only removing some from the middle breaks the history check. The cost is quality and cache: the model doesn't see its earlier reasoning across turns. The fix is carrying the blocks opaquely through the contract (a TODO).

**Q: Why prompt caching in the gateway?**
An agent resends its whole history on every turn, so turn N repeats turns 1..N-1. With caching, that repeated prefix is billed at a fraction of the price and processed faster.

**Q: How does the gateway contract evolve without breaking clients?**
New fields are optional with defaults, the same way the queue payload grows.

**Q: Why does the client refuse options like `stop` or `tool_choice` instead of ignoring them?**
Silently ignoring an option changes behaviour without anyone noticing. Newer models also reject forced tool choice, so the contract doesn't have it.

## Agentic indexing

**Q: Why an agent instead of one LLM call with the file list?**
One call has to fit the whole repo into one prompt, so big repos get only a folder summary. An agent explores the checkout with read-only tools and reads only what it needs; each sub-agent's context covers only its part. The cost is more calls, more time, and the need for budgets and sandboxing.

**Q: Why does your code start the sub-agents instead of letting an agent spawn them?**
Validation, recursion, parallelism and cost stay deterministic and testable. An agent that spawns agents is much harder to bound and to test.

**Q: Why level by level?**
All areas of one level are split in parallel, then the next level. No agent waits on another inside the thread pool, so a bounded pool can't deadlock (a worker waiting on a child task that needs a free worker).

**Q: How does the recursion end without a depth limit?**
A validation rule: no area may hold every file its parent holds, so each level strictly shrinks; a fallback child is a strictly deeper folder. Scopes with a single file are never given an agent. The file sets shrink every level, so it terminates.

**Q: Why fall back per node instead of failing the job?**
With 20–40 agents per repo, if each fails validation twice just 2% of the time, a 30-agent job fails 1 − 0.98³⁰ ≈ 45% of the time, and one bad node throws away the whole tree. Per-node fallback (its children become its subfolders, marked `grouping = fallback`) keeps the tree validated, just plainer in places.

**Q: What's the contract on an agent's answer?**
Every path must exist and lie inside the agent's scope, names are non-blank and unique among siblings, the top level has at least one area, and no area covers its whole scope. It's checked with Pydantic validators that receive the agent's `Workspace` as validation context, so they compare the answer with facts the model can't change. A rejected answer goes back as the tool result for one retry.

**Q: Why do the limits exist, and why not limit the tree's shape?**
The shape limits (depth, children per node) were dropped. What remains protects cost and the context window: a turn ceiling per agent that stops runaway loops, a "wrap up, you have N turns left" message before the hard stop, and a 300-line cap per tool result (the agent can narrow its query). The numbers are guesses until the per-agent logs give real ones.

**Q: Why stop softly before stopping hard?**
A hard stop throws away everything the agent learned. Telling it the budget is used and giving it a few turns lets it submit its best answer; the hard stop is still there so a confused agent can't run forever.

**Q: How do you stop a tool from reading `/etc/passwd`?**
Every tool reads through `Workspace`, which rejects absolute paths, `..`, and paths outside the agent's scope, then resolves the real path and checks it's inside the checkout. That last check catches tracked symlinks pointing outside the repo.

**Q: Why run grimp in a separate process?**
grimp finds packages with `importlib.util.find_spec`, which searches `sys.path`. In the worker, a repo package named `app` would resolve to our own `app`. A `python -I` subprocess has only the checkout on its path, and the untrusted repo stays out of the worker's memory. A test proves it with a repo whose package is called `app`.

**Q: Why does community detection need a fixed seed, and why break ties by name?**
Louvain is randomized, and grimp's module order varies between runs. The same repo should give the agent the same text every time, for reproducible results and stable tests.

**Q: Could an agent leak secrets from the repo?**
Anything in an agent's file list can be read and ends up in a prompt, i.e. at the LLM provider. So files that commonly hold secrets (`.env*`, private keys, `.npmrc`, `credentials.json`) are filtered out before the agents ever see the list; `Workspace` then refuses any file not on it. Found in the first dry run on this repo, whose `.env` was visible.

**Q: What about prompt injection from repo files?**
The tools are read-only and confined to the checkout, every answer is validated before it reaches the database, and the system prompt says tool output is data and instructions inside files are ignored. Below that, the worker runs in a sandbox container: even a fully steered agent can't write outside `/tmp`, gain privileges or reach any host but the git hosts.

**Q: What's the cost of the agentic indexer if a job fails late?**
Everything finished in memory is lost, and the retry pays for every agent again. A per-node result cache keyed on (repo, commit, node), which never goes stale because the commit is pinned, is listed after v1.

## Concurrency

**Q: How do you cap agents at 3 across all workers?**
A Redis counting semaphore with leases (`app/queue/semaphore_slot.py`): a sorted set of holders scored by lease expiry. One Lua script drops expired entries, and if fewer than 3 remain, adds ours; a waiting worker polls with jitter. Release is `ZREM` in a `finally`. Leases free the slots of crashed workers, and the script reads the clock from Redis (`TIME`) so workers with skewed clocks can't expire each other's leases early.

**Q: An agent runs for minutes. How does it keep its slot without a huge lease?**
A heartbeat thread renews the lease every third of its length (60 s lease, renewed every 20 s), so a dead worker's slot frees itself within a minute while a live one keeps it. Renewal only extends a lease that hasn't run out: once it has, another worker may hold the slot. If that happens (the process stalled), the agent finishes over the limit and it's logged; killing it would waste its work.

**Q: Why not a list of 3 tokens with BLPOP/RPUSH?**
Simpler and no polling, but a crashed worker never returns its token: after three crashes the system is stuck forever.

**Q: Why does a slot cover a whole agent and not one LLM call?**
The goal is protecting the machine, not the gateway: an agent's tools (git grep, parsing files, reading the checkout) cost CPU and memory between LLM calls, so the cap has to cover the whole run. Per call would limit only requests in flight and needs no heartbeat, but lets any number of agents run tools at once. The cost of per agent: lease renewal, and a slot that's held while the agent waits on the model.

## Deep dives

**Q: Walk me through generating a deep dive.**
`POST /nodes/{id}/deep-dive` queues `{node_id}` once (Lua `SET NX` + `XADD`) and returns 202. A worker skips the job if the node already has a row, sparse-clones only the node's paths at its snapshot's commit, runs an agent over that checkout, renders the typed answer to HTML, uploads it to a bucket under `sha256(html).html`, inserts the row, then `XACK`s.

**Q: Why does the model return a typed answer and not HTML?**
Three reasons. Safety: repo files can carry prompt injection, and model-written HTML could smuggle a `<script>` into a page we serve. Truth: code excerpts are a path + line range that our code copies from the checkout, so the model can't invent code. Control: one template means a consistent look, and new media is a new block type, not a prompt change.

**Q: How do you stop the page from running injected scripts?**
Two layers. Jinja2 autoescape turns any `<` in model text or repo code into `&lt;`, and the only markup we add (`<code>` for backticks) is added after escaping. Then a CSP with `default-src 'none'`, both in the page and as a response header, so even a missed escape can't run a script or call out.

**Q: Why store HTML in a bucket instead of a Postgres column?**
Pages will grow with images and video, and large blobs bloat the table, its backups and its replication. A bucket is cheap, durable, and serves bytes without touching the database. Postgres keeps what it's good at: the node → page link, with a unique constraint.

**Q: Why name the object by its hash?**
Content addressing makes the write idempotent: a retried job that renders the same page writes the same key, so retries can't pile up copies, and a key never changes meaning, so it can be cached forever. If the model writes a different page on retry, the old object is an orphan, which costs a few KB and nothing else.

**Q: Why upload before inserting the row?**
Crash between the two: upload-first leaves an orphan object, and the retry overwrites it. Insert-first leaves a row pointing at nothing, which the API would serve as a broken page. Pick the failure that's harmless.

**Q: Why one deep dive per node?**
The node is pinned to a commit, so its code never changes and a second deep dive would just cost money. The unique constraint on `node_id` makes the database enforce it, and also serves the lookup. A zombie worker that finishes second hits `ON CONFLICT DO NOTHING`.

**Q: Why no status column?**
"No row" already means "not written yet", and the dedup marker means "queued". A status column would need updates from the worker on every transition and could disagree with the queue. It comes back if the UI needs "failed".

**Q: How does the sparse clone work, and why fetch by SHA?**
`git init`, `remote add origin -- <url>`, non-cone `sparse-checkout set /<path>`, `fetch --depth 1 --filter=blob:none origin <sha>`, `checkout --detach`. Blobs are fetched lazily, only for the checked-out paths, so a big repo costs a few files. The branch may have moved since indexing, so fetching the branch could give different code than the map describes. GitHub and GitLab allow fetching a commit by SHA.

**Q: How is the sparse clone hardened?**
The SHA must be 40 hex characters, so it can't be an option like `--upload-pack=...`. The URL comes after `--`. Every sparse pattern starts with `/`, so none can start with `-`. The repo URL itself was allowlisted when the repo was added. git runs with no system or global config and no terminal prompt.

**Q: How do you make the AI text not sound like AI?**
The humanizer rules, split by how reliably a regex can check them. Tells that are wrong almost everywhere (em dashes, words like "delve" or "pivotal", phrases like "let's dive in") are enforced: every text field has the `Prose` type, whose validator rejects the answer and lists every hit. Rules that need judgment (sentence-case headings, lists of three, closing one-liners) are in the prompt only.

**Q: Why not enforce every writing rule in the validator?**
A rejection costs a full extra LLM call, and the agent gets one retry: two rejections fail the deep dive. A heuristic like "is this heading Title Case?" misfires on product names (Redis, FastAPI), so it would fail good answers. Only checks with almost no false positives earn the right to reject.

**Q: The validator and the prompt both list banned words. How do they stay in sync?**
They're the same list. `humanizer_rules.py` holds it, the validator reads it, and the prompt template has `{banned_words}` placeholders filled from it at load time.

**Q: Why tell the model the rules if you validate anyway?**
Prevention is cheaper than correction. Without the rules up front, most first answers would be rejected, and each rejection is a full extra turn with the whole conversation as input.

**Q: What does "Hello Interview style" mean concretely?**
An order: opening, a worked example through real functions, core concepts, internals with real numbers, one section per job, what breaks and the fix, design choices framed as "gives A, but costs B", interviewer questions as headings, summary. Plus tip/info/warning callouts, four to seven per page. The model writes its own headings so 30 pages don't read like one template.

**Q: What's the optional tech stack part?**
For areas built on technologies worth defending (Redis Streams, SQLModel), the answer can carry a `tech_stack` list: each with its role here, pros, cons, alternatives with trade-offs, and how it fits the overall design. It's a typed field, so the renderer gives it a fixed layout, and it's empty for plain application code.

**Q: Why `run_agent` and not LangGraph?**
Today there's one expensive step, the agent. LangGraph's value is checkpoints between steps, so a failed later step doesn't redo earlier ones. That pays off when image or video generation becomes a second expensive step. Until then it would be a framework wrapped around one function call.

**Q: Indexing and deep dives both run agents. How do you keep them from overloading the gateway?**
Both hold a slot from the same Redis semaphore (same key, same limit of 3) for a whole agent run. The limit is imported from one place, because two services passing different limits to one semaphore would break the cap.

**Q: The agent runs for minutes. What about the database session?**
The worker reads the node and repo, then ends the transaction before the agent starts. Otherwise a connection would sit "idle in transaction" for minutes, holding a pool slot and blocking vacuum. The insert at the end opens a fresh one.

**Q: What if the node is deleted while its job is queued?**
Its repo was removed and the node cascaded away. The worker logs it, drops the job and acks, since retrying can't help.

**Q: What breaks today?**
The HTML is proxied through the API, which spends API bandwidth; presigned URLs fix that at scale.

**Q: The pages have diagrams. How do they get there if the page runs no scripts?**
The model writes the diagram as text (Mermaid or Graphviz DOT), never as markup. During validation of its answer, that text is sent to a self-hosted Kroki, which returns SVG; the SVG is kept on the block and the template embeds it as `<img src="data:image/svg+xml;base64,...">`. Rendering happens on our side, so the page keeps `default-src 'none'`.

**Q: Why render during validation and not when building the page?**
So a broken diagram is caught while the agent can still fix it. Kroki's syntax error becomes a Pydantic `ValueError`, which goes back to the agent as a normal rejection, like a bad line range. At page-render time the only choices would be to drop the figure or fail the job after the expensive agent run.

**Q: What if Kroki is down?**
That's an `httpx` error, not a `ValueError`, so Pydantic lets it propagate out of `model_validate`. The job fails, the queue redelivers it, and after `JOB_MAX_DELIVERIES` it's dead-lettered. The point is who can fix it: the agent can fix syntax, only an operator can fix a dead service, so the agent's two attempts aren't wasted on it.

**Q: Why Kroki instead of mermaid-cli or a public renderer?**
mermaid-cli puts Node plus a headless Chrome into every Python worker. mermaid.ink sends repo content off the machine. Graphviz alone has no sequence diagrams. Kroki is one HTTP call for both languages, and its default safe mode stops model-written DOT from using `image=` to read files on the renderer.

**Q: You also let the model write raw SVG. Isn't that an injection risk?**
The SVG is base64-encoded into an `<img>` attribute, never inlined as markup, so it can't break out of the page. A browser renders an SVG image in a sandbox with no scripts, no external loads and no DOM access. On top of that the validator requires well-formed XML, an `<svg>` root in the SVG namespace, a `viewBox`, no `<script>`, and under 40 KB. The cost of `<img>` is that the figure can't pick up the page's dark-mode colors, so the figure is forced white.

**Q: How does the validator get at Kroki?**
Through the Pydantic validation context. It used to be the bare `Workspace`; now it's an `AnswerContext(workspace, render_diagram)` built in `write_deep_dive`, where `render_diagram` is `partial(render_svg, httpx.Client(base_url=KROKI_URL))` bound in `make_write`. The wrapper (`app/kroki/`) takes a client and knows nothing about deep dives, same pattern as the storage wrapper.

**Q: How do you make sure every section actually gets a visual?**
A `model_validator` on `DeepDiveAnswer`, not on `Section`: a section can't know whether it's the summary, the answer can. It takes every section but the last (when there are several), checks for a `Diagram` or `SvgFigure` block, and rejects with every missing heading in one message so the agent fixes them all in its single retry. The summary is exempt because it adds no new claim worth drawing. The prompt also says which visual fits which section, since a rejection costs a retry and two rejections fail the run.

**Q: Why isn't the diagram source checked by the humanizer rules?**
`-->` and `--` are Mermaid and DOT syntax, and the dash check would reject every arrow. Only the caption is `Prose`.

## Agent sandbox

**Q: What can a hostile repo do to your worker, and what stops each attack?**
Git tricks (filters, hooks, odd URL schemes): git ignores system and global config, a repo can't ship its own, git-lfs isn't installed, and git may only speak https. Prompt injection: the tools are read-only and every answer is validated. Breaking out: the worker is non-root, has no capabilities and can't gain privileges. Exfiltration or attacking other hosts: the container's network has no route out, and the only proxy allows the three git hosts.

**Q: Why an egress proxy instead of splitting the clone and the agent into two containers?**
The proxy is one container and a short config, and the job flow stays the same. A split is stronger (the agent container has no network at all), but every job then needs a handoff through a shared volume. gVisor or Firecracker make sense once repo code actually runs; today nothing executes it.

**Q: The agent's tools are already read-only. Why sandbox at all?**
Defense in depth. A bug in a tool, in git or in grimp's parser shouldn't turn into host access. Each layer assumes the one before it failed.

**Q: How do the workers reach Postgres and the gateway but not the internet?**
They're only on a compose network marked `internal`, which has no route out. Postgres, Redis, MinIO, the gateway and Kroki join that network as well as the normal one, so the workers can reach them and the host keeps its published ports. `NO_PROXY` keeps that internal traffic away from the proxy.

**Q: What does a read-only root filesystem plus tmpfs give you, and what breaks?**
Nothing persists between runs, and malware has nowhere to stay. Anything that writes outside `/tmp` breaks, so `PYTHONDONTWRITEBYTECODE` is set. The 1 GB tmpfs also caps repo size: a bigger clone fails with "no space", retries, then lands in the DLQ.

**Q: What does `cap_drop: ALL` with `no-new-privileges` actually stop?**
Even root in a container has some kernel powers (raw sockets, chown, binding low ports). Dropping all of them removes those. `no-new-privileges` stops a setuid binary from raising privileges, so the non-root user stays non-root.

**Q: The proxy's host list duplicates `allowed_hosts.py`. How do you stop drift?**
A test parses `squid.conf` and asserts the list equals `ALLOWED_HOSTS`. Generating the config from Python was rejected: a build step for three lines.

**Q: Why isn't the LLM API on the proxy's allowlist?**
The workers never call it. They call the gateway, which sits on the internal network and holds the key. So the worker container has no key and no route to the provider.

**Q: What can still leak?**
File contents, through the agent's answer to the LLM. That's inherent to sending code to an LLM. `code_files` drops secret files before the agent ever sees the list.

**Q: How would this look on Kubernetes?**
A NetworkPolicy replaces the internal network, a pod `securityContext` (`runAsNonRoot`, `readOnlyRootFilesystem`, `capabilities.drop: [ALL]`, `allowPrivilegeEscalation: false`) replaces the compose flags, an `emptyDir` with `medium: Memory` replaces the tmpfs, and an egress gateway or mesh rule replaces Squid.

**Q: A deep dive runs two agents. What happens if the worker dies after the first one?**
The two agents are nodes of a LangGraph with a Postgres checkpointer, one thread per node id. After each node the state is saved. On redelivery the worker reads the thread: if it's unfinished it invokes with `None`, which resumes at the node that didn't complete; if it finished but the row never got inserted (today's case, a missing table), the stored answer is reused and no agent runs at all. The thread is deleted after the commit.

**Q: Why not just checkpoint by hand, a JSON file in the bucket?**
That was the alternative, about 60 lines. LangGraph was already planned for the point where a second expensive step appeared, and it gives the resume semantics, the state store and the tooling (time travel, inspection) with the same amount of code. The cost is two dependencies and a set of tables Alembic doesn't own.

**Q: What's stored in the checkpoint, and why not the Pydantic answer object?**
The answer as plain JSON (`model_dump(mode="json")`). A `Diagram` block has a validator that renders through Kroki and needs the checkout, so the object can't be rebuilt from a checkpoint in isolation. Whoever reads the state re-validates with the live context, which re-renders the diagrams (cheap, deterministic) and re-checks code excerpts against the fresh clone.

**Q: Why does the checkpointer have its own connection?**
`PostgresSaver` needs autocommit: each checkpoint write must land immediately, independent of the job's transaction. The job's SQLAlchemy session runs the row insert inside a transaction. Mixing them would either commit the job early or hold checkpoints until the job commits, which defeats the point.

## Reliability (leases, reaper, DLQ)

**Q: Walk me through a job's life.**
`XREADGROUP` hands it to one worker and puts it in the group's pending list. While it runs, a heartbeat thread renews the lease every 20 s. Success: commit, then `XACK`. Failure: no ack, the heartbeat stops, and after 60 s idle any worker's loop reclaims it with `XAUTOCLAIM`. On the 4th delivery it's moved to a dead-letter stream instead of run again.

**Q: Where does the reaper run?**
Inside every worker's loop: before reading a new job, it tries to reclaim one abandoned job. No separate process to deploy or monitor, and it runs as long as any worker runs. Abandoned jobs go first, so old work isn't starved by new work.

**Q: Why a heartbeat instead of a long lease?**
An index job can run for many minutes. A lease sized to the longest job would leave a crashed worker's job stuck that long. A short lease that's renewed detects a dead worker within 60 s and still lets a live one run for hours.

**Q: How does the heartbeat renew the lease?**
`XCLAIM <id> … min-idle 0 JUSTID` to itself resets the entry's idle time. `JUSTID` matters: it doesn't bump the delivery count, so renewals don't push a healthy job toward the DLQ.

**Q: The worker stalls for 90 s (GC pause, laptop sleep). What happens?**
The reaper gives the job to another worker. When the first one wakes, its renewal script sees with `XPENDING` that it no longer owns the entry, so it doesn't steal it back (a plain `XCLAIM` would), logs a warning and finishes. Two workers then run the same job, which costs money but not data, because both end in an insert-once write.

**Q: Then what stops a zombie from overwriting newer work? Where's your fencing token?**
Almost nothing is overwritten. Final writes are `INSERT … ON CONFLICT DO NOTHING` on a unique key (`repos.url`, `snapshots(repo_id, commit_sha)`, `deep_dives.node_id`). The first commit wins and the late one does nothing; the deep dive's object key is the hash of its content, so even a zombie's upload is harmless. The one overwrite is the repo's current-snapshot pointer, and that one has a fence: `head_seen_at`, see "Re-indexing".

**Q: Why is the retry delay a full lease? Isn't that slow?**
It's free backoff: a failed job is simply left un-acked, and the reaper picks it up once it's been idle for a lease. A failure that's caused by the gateway being down or overloaded gets a minute to recover instead of being hammered. No timers or retry scheduler.

**Q: Why dead-letter at all? Why not retry forever?**
A poison job (bad payload, a repo that always breaks the clone) would burn LLM money and a worker forever. After 3 deliveries it goes to `dead:index` / `dead:deep_dive` with its original id, where a human can inspect it.

**Q: Why delete the dedup marker when dead-lettering?**
The marker makes POST idempotent, and it has no TTL. If it stayed, `POST /repos` would answer 202 and enqueue nothing, forever, so the repo could never be retried. Deleting it lets the user add it again.

**Q: How does the queue layer know which marker to delete without knowing about repos?**
Each job carries its own `dedup_key` field, written by the same enqueue call that set the marker. That also works when the payload itself is broken, which is exactly the case most likely to be dead-lettered.

**Q: Why is dead-lettering one `MULTI` and not Lua?**
`XADD` to the DLQ, `XACK`, `DEL` marker must all happen or none: acked but not in the DLQ is a lost job; in the DLQ but still pending runs it again. There's no read-then-decide step, so a transaction is enough. The enqueue needs Lua because it branches ("XADD only if SET NX succeeded").

**Q: Why not mark the repo `failed` in Postgres?**
No repo row exists while a repo is being indexed; the worker creates it at the end. Inserting a `failed` row would make the next attempt's `ON CONFLICT (url) DO NOTHING` hit it and silently drop the new tree. The DLQ is the record of failure.

**Q: How does a deploy avoid killing a running job?**
SIGTERM sets a stop flag. The loop finishes the current job, acks it, and exits; an idle worker exits within one 5 s read block. If the orchestrator kills it anyway (grace period too short for an index job), the reaper recovers the job after one lease, so it's slower, not lost.

**Q: What breaks today?**
Each reclaim starts at the oldest pending entry, and `XAUTOCLAIM … COUNT 1` looks at only about 10 entries per call. If more than 10 jobs are running at once, an abandoned job behind them is never found. Today the pending list is about the number of running workers, so it holds; the fix is to keep the cursor `XAUTOCLAIM` returns and continue from it. The DLQ has no tooling: replaying a job is a manual `XADD`. And under Redis Cluster, the stream, its DLQ and the markers need one hash tag so the `MULTI` stays on one slot.

**Q: Why are interview questions a typed field and not just sections with "?" headings?**
They get stored as rows for self-quizzing, so they need to be data, not something guessed from heading punctuation. As a field, the validator enforces 3 to 6 of them and checks their prose; the renderer gives them a fixed quiz layout; and the worker writes them in the same transaction as the deep dive row, so a page never exists without its questions. The draft model extends the table's base class, so the question/answer shape is declared once.

**Q: Why does the page hide answers behind `<details>`?**
Retrieval practice: trying to answer before seeing the answer is remembered far better than rereading (the testing effect). The questions are also listed at the top of the page, so the reader knows what to look for while reading. It's native HTML, so it works with no JavaScript, which the page's CSP forbids anyway.

**Q: What happens when someone adds a private or non-existent repo?**
`POST /repos` runs `git ls-remote --exit-code -- <url> HEAD` before queueing, with `GIT_TERMINAL_PROMPT=0` so git fails in about two seconds instead of waiting for a password. The route turns `CalledProcessError` into a 400 whose detail is git's `fatal:` line, and `TimeoutExpired` into a 400 as well; nothing is queued. Before this check the job reached the worker, failed three times, was dead-lettered, and the UI only learned about it when its 15-minute poll gave up. The rejected alternatives: a `failed` row (the design keeps no failed rows because the next attempt's `ON CONFLICT` insert would silently drop its tree), and a job-status endpoint (more surface than the problem needs). The wrapper lives in `app/git/` and knows nothing about repos; the route binds it to the timeout in `app.config`.

**Q: Isn't a network call inside a POST handler a bad idea?**
It costs one round trip, bounded by `GIT_LS_REMOTE_TIMEOUT_S` (15 s), and it buys an immediate, specific answer for the common mistake. The trade is latency for the one person adding a repo against a 15-minute silent wait. If adds became frequent or the handler had to stay under a tight budget, the check would move into the worker with a status row and a job endpoint. Tests monkeypatch the wrapper in the route so the suite never touches GitHub; the wrapper itself is tested against a local `file://` repo.

**Q: How do private repos work?**
GitHub OAuth. The browser goes to `/auth/github/login`, which sets a random `state` cookie and redirects to GitHub with scope `repo`. GitHub calls back with `code` and `state`; the route checks the state against the cookie in constant time, trades the code for an access token (`app/github/exchange_code.py`), asks GitHub who the user is, and upserts a `users` row keyed by GitHub's stable numeric id, so a renamed login is still the same user. The token is stored Fernet-encrypted; the session cookie holds only a signed user id. When a logged-in user adds a repo, the job payload (`IndexJob`) carries their user id, and both workers build a git environment from it (`app/auth/git_env.py`): `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=Authorization: Basic base64(x-access-token:TOKEN)`. Environment, not `-c`, so the token is not in `ps`; scoped to the origin, so a redirect elsewhere does not get it.

**Q: Why an OAuth App and not a GitHub App?**
A GitHub App is the better product answer: fine-grained per-repo permissions, installation tokens that expire in an hour, and no personal token at rest. It costs an installation flow, a private key, JWT signing and token refresh in the workers. For a single-tenant tool on one machine, the OAuth App gets the private repo indexed with two routes and one table. The trade is written down: `repo` scope also grants write, which the app never uses but a leaked token would have.

**Q: Why is the token in Postgres and not in Redis with a TTL?**
A deep dive can be requested days after indexing, and it clones the repo again. A Redis entry that expired with the login session would silently break every deep dive of a private repo. Postgres keeps the token for as long as the user row exists. The cost is a secret at rest, hence Fernet under `SECRET_KEY`, and a stated limit: rotating `SECRET_KEY` orphans every stored token and logs everyone out.

**Q: Why does `IndexJob` exist next to `RepoCreate`?**
`RepoCreate` is what the browser sends. If `user_id` lived on it, a client could pick whose token the worker uses. `IndexJob` extends it with `user_id` and is only ever built server-side, from the session cookie. Same validation, one extra field, and the trust boundary stays where the HTTP body is parsed.

**Q: What does this do to the sandbox story?**
Nothing changes in the egress allowlist: the worker still only talks to github.com. The API process, which was never sandboxed, now also calls `api.github.com` and `github.com/login/oauth`. What is new is that a worker now holds a secret in its environment for the duration of one git call. A prompt-injected repo still cannot read it: agents' tools read files in the checkout, not the worker's environment, and the agent process never runs git.

## Frontend

**Q: How does the frontend know the API's types?**
It doesn't write them. `npm run types` imports the FastAPI app in Python, dumps `app.openapi()` to a JSON file, and `openapi-typescript` turns that into `schema.d.ts`. The SQLModel classes stay the single source: Python can't share code with TypeScript, so the OpenAPI spec is the bridge. Cost: the file must be regenerated after a model change; `tsc` fails the build if a component depends on a field that moved.

**Q: Why a Vite proxy instead of CORS on the API?**
CORS is a browser rule about two origins. The dev server proxies `/repos` and `/nodes` to uvicorn, so the browser sees one origin: no preflight, no credentials flags, and the deep dive page's CSP behaves exactly as it will in production, where the built bundle is served by FastAPI itself. `CORSMiddleware` is one more thing to configure per environment and to get wrong.

**Q: Why React Flow? Isn't a nested list enough for a tree?**
The map endpoint returns `{nodes, edges}`, which is exactly what React Flow consumes, and the design keeps `relates` edges for later: cross-links between areas don't fit a nested list. React Flow has no layout engine; the first version used dagre to draw the whole tree, which made 50 areas unreadably small, so now one scope is drawn per screen (parent card plus a column of children), which needs no layout engine at all. If the UI were only a tree, nested `<details>` would be the honest smaller answer.

**Q: How do the scope transitions work?**
The clicked card keeps its React Flow id when it becomes the scope, so React Flow moves the same element and a CSS transition on its transform slides it into the parent slot. New children and edges run a keyframe fade-in. The camera eases with `setCenter` onto the scope card, keeping the current zoom, from an effect that waits for `useNodesInitialized()`; the card is placed at the vertical middle of its children, so centering on it centers the level. `fitView` runs only on first mount. `prefers-reduced-motion` disables all three.

**Q: How does the UI show progress with no job endpoints?**
Polling, because that's the only signal the API offers: `GET /repos` every 3 seconds after an add, `GET /nodes/{id}/deep-dive` every 3 seconds after a request, each with a 15-minute give-up. The cap matters because a dead-lettered job never produces a row, so without it the UI would wait forever. SSE replaces this once job endpoints exist; the scaling notes in DESIGN §10 cover the connection cost.

**Q: How do errors from the API reach the user?**
One `request` helper turns every non-2xx into `ApiError(status, detail)`. FastAPI puts a string in `detail` for `HTTPException` and a list of `{loc, msg}` for 422 validation errors; the helper handles both so components only ever show a message. A 503 from the queue says "retry", because the API wrote nothing.

**Q: How does the UI decide whether to show the deep dive or the Generate button?**
It asks `GET /nodes/{id}/deep-dive`. A 200 means the page exists; a 404 means not yet. There is no status field because the backend has none by design: no row means not written. So the panel treats 404 as data, not as an error, and only other statuses are shown as errors. After a POST it polls the same GET every 3 seconds until a row appears or 15 minutes pass.

**Q: Why reset component state with `key` instead of an effect?**
Changing `key` unmounts and remounts the component, so React throws the old state away with no code of mine. An effect that resets state on a prop change runs after the first render with the stale state, so the user sees one wrong frame. The canvas uses `key={repo.id}` for its scope; the node panel uses `key={node.id}` for its status.

**Q: Why an `<iframe>` with `sandbox` when the page already has a CSP?**
Two independent layers. The CSP travels with the page and forbids scripts from inside; `sandbox=""` forbids scripts, forms and popups from the embedding side, even if someone later serves the page without the header. Both are cheap; defense in depth against prompt-injected repo content, which is the same reasoning as autoescaping plus CSP in the renderer.

**Q: How is the frontend served in production, and why not always?**
FastAPI mounts `frontend/dist` at `/` with `StaticFiles(html=True)`, after the routers so it can't shadow `/repos` or `/nodes`. The mount is conditional on the folder existing: `StaticFiles` raises on a missing directory, and the test suite and API-only deploys have no bundle. In dev, Vite serves the source with hot reload and proxies the API instead.

**Q: What would you change first at scale?**
Replace polling with job endpoints plus SSE (the API design already reserves it), code-split React Flow out of the main chunk (it's most of the 530 kB), and move `scopeView` to a server query (`GET /nodes/{id}` already returns children) if maps grow to thousands of areas, since the one-shot `/map` download is the next bottleneck after that.

## Agent runtime: the Claude Agent SDK wrapper

**Q: What is the Claude Agent SDK, and why is it in the project?**
Claude Code packaged as a Python library (`claude-agent-sdk`). You hand it a prompt and options; it spawns the bundled Claude Code binary, which runs the whole agent loop: calls the model, runs tools, keeps the conversation, retries. The project has its own loop (`run_agent`, LangChain). The SDK is a second runtime for the same agents, selectable by a setting, so both can be measured against each other and the agents can run on the developer's own Claude Code login instead of the API key when they run on the host.

**Q: Why does it replace the loop and not the chat model?**
Because the SDK never hands a tool call back to the caller. It executes tools itself, in-process, and only returns the final result. The gateway contract is one model turn per request with the worker executing tools, so the SDK cannot sit behind it. The right seam is `run_agent`, which all three agents call with the same signature: system prompt, task, tools, answer schema, turn budget.

**Q: How do the LangChain workspace tools reach the SDK?**
`to_sdk_tools` turns each `BaseTool` into an in-process MCP tool. Name, description and JSON schema come from LangChain's own `convert_to_openai_tool`, the same call the gateway uses for its tool specs, so one source of truth for the schema. The handler invokes the tool with a whole tool call, which makes LangChain return a `ToolMessage` whose `status` says whether it failed; that maps to MCP's `is_error`. The call runs in a thread because the tools do blocking file IO and the SDK's handlers run on its event loop.

**Q: The binary runs next to a repo you did not write. How do you stop that repo from influencing it?**
Three options. `tools=[]` removes every built-in tool (Read, Bash, Write), so the workspace tools are the only way into the checkout. `setting_sources=[]` stops it loading settings files, including project ones, which can define hooks that run commands. `strict_mcp_config=True` limits MCP servers to the one the wrapper passes. The last two also fixed a cost bug: without them the first live run loaded the developer's own MCP servers from `~/.claude.json` and sent 400k tokens of their tool schemas on a three-turn Haiku call.

**Q: How does the wrapper tell "no answer" from "failure"?**
Same split as the gateway. An unusable answer is a result, not an exception: `SdkResult.answer is None`, with `out_of_turns` saying whether the turn budget ran out, so the domain layer can nudge, wrap up or fall back. A failure of the binary or the API raises `AgentSdkError`, which fails the job so the queue retries it. The CLI reports "out of turns" as an error result, sometimes as a raised exception and sometimes as the final message depending on its exit code, so both paths feed one `_no_answer` function.

**Q: Why `asyncio.run` inside a sync function?**
The SDK is async; the workers and the agent loop are sync, and the indexer runs sibling agents from a thread pool. One event loop per call means each thread gets its own loop and its own binary process, with nothing shared. The stream is read to its end on purpose: returning out of the `async for` early left the generator open, and `asyncio.run` then tried to close it while it was running.

**Q: How is the answer validated?**
The SDK is asked for JSON in the Pydantic model's schema (`output_format` with `json_schema`); it adds a `StructuredOutput` tool and retries schema violations itself. The wrapper only checks the result is a JSON object. The domain layer runs the real validators, including the ones that compare the answer with facts outside the model's control, and resumes the session with the error when they fail.

**Q: What about billing and the subscription?**
The binary uses `ANTHROPIC_API_KEY` if it is in its environment and the host's Claude Code login otherwise. `AgentSdkSettings.env` carries that choice, empty for the login. The subscription path is for workers run on the developer's own host; the Docker workers have no login and stay on the gateway with the API key. Anthropic's terms do not allow offering claude.ai login to third parties in a product, so this is a developer convenience, not a deployment option.

**Q: How do you test a wrapper around a subprocess?**
The conversion layer is pure and has unit tests: schema and description come through, a good call returns text, bad arguments and `ToolException` become `is_error` results instead of exceptions. The run itself has no fake binary; a live check with Haiku covers the three outcomes (answer, out of turns, resume with a wrap-up) and costs well under a cent. A fake of the SDK's message stream would test my assumptions about the SDK, not the SDK.

**Q: What does the SDK give you that your own loop does not, and what does it cost?**
It keeps thinking blocks across turns (the gateway contract drops them), caches prompts automatically, retries API errors, and it is less loop code to own. It costs a 0.2.x dependency whose API moves, a Node binary per agent run, no control over caching or per-turn requests, and a client-side cost estimate instead of real usage.

## Library and practice pages

**Q: Why does each list item carry the node name and repo URL instead of just ids?**
The page needs them to label and group every row. Ids alone would mean one more request per row, or a second call to join on the client. The join is one SQL statement on primary keys. The item class extends the existing `XRead` and adds only those labels, so the shared fields are declared once.

**Q: Why no pagination?**
It is one person's bank: tens of deep dives and a few hundred questions. Pagination would add a cursor, a "load more" control, and server-side filtering, for no visible gain. The endpoints carry a TODO with the trigger: a cursor on `created_at` once the list passes a few hundred rows.

**Q: Why an index on `deep_dives.created_at` for such a small table?**
The project rule is an index for every query the API makes, so the plan does not change when the table grows. At today's size Postgres will still pick a sequential scan, and that is fine. The cost is one more index to update on each insert, and deep dives are inserted a few times a day.

**Q: How do you shuffle the questions, and why not `sort(() => Math.random() - 0.5)`?**
Each item gets one random key, and the copy is sorted by the keys. Every order is equally likely. A random comparator gives the sort inconsistent answers about the same pair, so some orders come out more often than others, depending on the engine's sort algorithm.

**Q: Why tabs in React state and not react-router?**
There are three views and no need yet for links to them. A router is a dependency, a route table and URL handling. The cost of skipping it: a refresh lands on the map, and you cannot bookmark the practice page. If links become useful, a hash value like the existing `#repo=` is the next step before a library.

**Q: Why open a deep dive in a new tab from the list, but in an iframe on the map?**
On the map the page sits next to the node it describes, so it is embedded. From the list, the page is the only thing you want to read, so it gets the whole window. Both load the same API route, which sends the CSP header, so the page runs no scripts either way.

**Q: Why is practice stateless?**
Tracking "got it / missed it" needs a table, a write endpoint, and a scheduling rule for when missed questions come back. Flashcards with a shuffle already cover the core job. Spaced repetition is the natural next step if the bank grows past what one sitting covers.

**Q: How do the agents choose between your loop and the Agent SDK?**
Through one Protocol, `AgentRunner`: system prompt, task, tools, answer schema, turn budget in; a validated answer or `AgentFailed` out. The three agents take a runner instead of a chat model. `make_runner` builds a small closure per runtime (`run_agent` with a `GatewayChatModel`, `run_agent_sdk` with the SDK wrapper) for every runtime the process's `AGENT_RUNTIMES` allows, and `dispatch_runner` wraps them in one runner that asks the dashboard setting which to use on each call. The factories for indexing and deep dives both call it, which also removed a duplicated model-construction helper.

**Q: How does the dashboard switch the runtime without restarting anything?**
The Settings page does `PUT /settings` with `{"agent_runtime": ...}`; the API stores it in one Redis key. Workers don't bind the runtime at startup: the runner they hold reads that key at the start of every agent call, one GET next to a model call that takes seconds. So the next agent, in a job already running, uses the new runtime. The GET and PUT share one Pydantic model, `AppSettings`, so the response and the body can't drift, and the frontend types come from the OpenAPI schema.

**Q: Why Redis for the setting, not a table?**
Same lifetime and same consumers as the agent slots and the dedup keys that are already there: the API writes, the workers read, and a missing key is a safe default. A table would add a model, a migration and a session per read for one toggle. If settings grow into something with history or per-user scope, that's the moment for a table.

**Q: What happens when the dashboard says `agent_sdk` and a Docker worker takes the job?**
`AGENT_RUNTIMES` says what a process may run; compose leaves it at `gateway`, so the Docker worker never builds the SDK runtime. When the setting asks for one it lacks, `dispatch_runner` logs a warning and uses the gateway. Failing the job instead would dead-letter it three retries later over a deployment mismatch. The cost of the fallback: with both a Docker worker and a host worker on the stream, the Docker one still bills the API key for the jobs it takes, so you stop the compose workers when everything should run on the login.

**Q: Why parse the runtime names in `make_runner` and not in `app.config`?**
An import cycle. `app.config` would import the enum from `app.agent`, whose package init imports `make_runner`, which imports `app.config` before it has defined the setting. So config keeps the comma-separated string and `make_runner` parses it into the `StrEnum` once at startup; a typo still fails before any job runs, which is what parsing in config would have bought.

**Q: How do you keep the two runtimes behaving the same?**
They share the nudge texts and the attempt limit from one module, raise the same `AgentFailed`, and validate the answer with the same Pydantic call and context. Explore's per-node fallback catches `AgentFailed` and the gateway's bad-answer error; an SDK process or API failure is a different exception on purpose, so it fails the job and the queue retries it, exactly like an unreachable gateway. One known difference: a follow-up in the SDK runtime gets a fixed `wrap_up_turns`, while `run_agent` gives whatever budget is left. That's a documented shortcut until the logs show agents that need more.

**Q: How is the SDK runtime tested without the binary?**
The SDK call is injected as a Protocol, so a scripted fake plays back results and records each call's prompt, turn budget and resume id. Tests cover a valid answer, a rejected answer that is fixed on resume, two rejections, out of turns with a wrap-up, a turn that ends without an answer and gets a nudge, no answer after the follow-up, and a missing session id. The plumbing itself was checked live by indexing a scratch repo on the host login.

**Q: How are code excerpts syntax-highlighted when the page runs no scripts?**
On the server, with Pygments, while the page is rendered. The CSP is `default-src 'none'`, so highlight.js or Prism could not run. Pygments emits `<span class="k">` style classes, and the colours for a custom Xcode-dark style (`XcodeDarkStyle`) are inlined into the page's `<style>`, scoped to `.code pre` so its global `pre` rules can't restyle the rest of the page.

**Q: Why lex the whole file instead of just the excerpt lines?**
An excerpt can start inside a docstring or a block comment. Lexed alone, that text would be coloured as code. The whole file is lexed once per path (cached), then the excerpt's lines are sliced out. Lexing with `stripnl=False` matters: by default Pygments strips leading blank lines, which would shift every line number.

**Q: The highlighted HTML is marked safe with `Markup`. Isn't that an XSS hole?**
Pygments escapes every token's text, and the HTML formatter closes each span at the end of its line, so splitting on newlines never cuts a tag in half. A test checks that `<` in source comes out as `&lt;` and that unknown file types fall back to escaped plain text. The CSP is still there as a second layer.

**Q: Why do code panels follow the page theme instead of staying dark?**
A tall black block on a white page is the heaviest thing on screen, and a deep dive has several. It pulled the eye away from the prose. Two palettes cost more colour checks, but Pygments makes that cheap: both use the same token classes (`k`, `s`, `c`), so the page ships both rule sets and `prefers-color-scheme` picks one. Diagrams can't do that: Mermaid draws for white, so their panel stays white in dark mode. In dark mode the white panel is dimmed slightly (`filter: brightness(.88)`), because the HIG says to soften white backgrounds that would glow against a dark page.

**Q: Why doesn't inline code have a grey background like most docs sites?**
The writer names a lot of identifiers, often eight or more per paragraph. With a box around each one, the paragraph read as confetti and nobody wanted to start reading it. The monospace face alone is enough to mark code; Apple's developer docs do the same.

**Q: Diagrams were shown at natural size before. Why shrink them now?**
The page mostly lives in a 560px side panel, so at natural size nearly every diagram scrolled sideways. Now they shrink to the column, but never below 45rem: under that, a sequence diagram's labels get too small to read, so a very wide one still scrolls inside its panel. Fullscreen gives it room.

**Q: How do you get Apple's fonts without loading web fonts?**
The CSP blocks font downloads, and SF Pro's licence doesn't allow serving it anyway. CSS has generic names that the browser maps to the platform's own fonts: `system-ui` is SF Pro on Apple devices, `ui-serif` is New York, `ui-monospace` is SF Mono. Each stack ends in fallbacks (Segoe UI, Consolas), so Windows gets its native fonts. The page uses one sans family for everything: a serif body next to monospace identifiers was three typefaces in one sentence.

**Q: Why not use Apple's system blue, #007aff?**
On white it's 4.02:1, under the 4.5:1 the HIG asks for normal text. The page uses #0066cc (5.57:1) in light mode and #2997ff (5.64:1 on the dark cards) in dark mode. Filled blue buttons take black text in dark mode, because white on #2997ff is only 3.0:1. Every colour pair was computed, not eyeballed.

**Q: Why does blue appear only on links and buttons?**
The HIG says not to use one colour to mean different things. Before, the accent marked links, the "Good to know" callout, the summary box, the current section and the contents hover. Now blue means "you can click this", and "Good to know" is grey. Each callout still carries a text label, so colour is never the only signal.

**Q: Why write a Pygments style instead of using the built-in `xcode` one?**
The built-in one is Xcode's light theme, and it's used in light mode. There's no built-in dark version, so the custom style takes its colours from Xcode's Default (Dark) theme, with one change: Xcode's comment grey is 3.7:1 on the panel, so it's lifted to 5.0:1. Pygments keeps the same short token classes (`k`, `s`, `c`), so pages already stored pick up the new colours as soon as they get the new stylesheet.

**Q: The icons used to be text glyphs. How do stored pages get the new SVGs?**
`restyle_html` upgrades a stored page in place: it swaps in the current stylesheet and replaces each old glyph span with the SVG from the same `icon()` helper the template uses, so the two can't drift. The icons are `aria-hidden`; the label next to each one ("Watch out") is what a screen reader reads.

## Focused deep dives and the whole-repo deep dive

**Q: How do you stop an LLM writer from producing a wall of text?**
Two layers. The prompt makes it choose first: name the three things the reader must leave with, and cut anything that doesn't serve them. Then a Pydantic validator enforces a budget: at most 5 sections, 900 words of paragraph and callout text, 4 callouts. An answer over the budget is rejected with the actual count and told to drop points, not shorten every sentence. The numbers live in constants that both the validator and the prompt read, so they can't disagree.

**Q: Why a nullable `node_id` and not a root node in the tree?**
The tree has no root node by design: top-level areas are nodes with no parent, and the repo row is the root. A fake root node would make every tree query filter it out. So a deep dive points at a repo always and at a node optionally; NULL means the whole repo.

**Q: How do you enforce "one root deep dive per repo" when `node_id` is NULL?**
A unique constraint on `node_id` doesn't, because Postgres treats NULLs as distinct. So there is a partial unique index on `snapshot_id WHERE node_id IS NULL` (one root page per snapshot, since re-indexing). The worker's insert uses `ON CONFLICT DO NOTHING` with no conflict target, so the same statement covers both the node key and the root key.

**Q: The migration adds a NOT NULL column to a table that already has rows. How?**
Autogenerate wrote it as one `add_column(nullable=False)`, which fails on existing rows. I edited it into three steps: add the column as nullable, backfill it from each row's node with one `UPDATE ... FROM nodes`, then set NOT NULL. The downgrade deletes root rows before making `node_id` NOT NULL again, because they can't exist in the old schema.

**Q: Dedup keys and LangGraph thread ids used the node id. What about the root?**
`DeepDiveBase.target_key` gives `str(node_id)` for a node and `snapshot-{snapshot_id}` for the root. Node keys kept their old format, so jobs and checkpoints already in flight during a deploy still match.

## Re-indexing (snapshots)

**Q: How does re-indexing work?**
A repo has many snapshots, one per indexed commit. Each snapshot owns its tree (nodes and edges) and its deep dives, and is never edited. A re-index clones HEAD, builds a new snapshot in one transaction, and moves the repo's `current_snapshot_id` to it. `/map` shows the current snapshot. Old deep dives stay readable and are tagged "older commit".

**Q: Why not update the existing tree in place?**
Three reasons. Every deep dive whose node changed or vanished would point at wrong paths. The tree would need a cycle check on every edge insert, because it is no longer built once top-down. And a half-finished update is visible to readers unless I lock a lot. A new snapshot avoids all three: readers keep seeing the old tree until the pointer moves, in the same commit that wrote the new one.

**Q: Why a snapshots table and not just a `commit_sha` column on nodes?**
The column is a smaller migration, but "one tree per (repo, commit)" can't be a unique key across many node rows. With a table, `UNIQUE (repo_id, commit_sha)` is the fence: a redelivered or zombie job hits `ON CONFLICT DO NOTHING` and builds nothing.

**Q: Two re-index jobs run at once. Which one wins?**
The one that read HEAD later, whatever order they finish in. Each job reads Postgres's `clock_timestamp()` before cloning. The pointer moves only `WHERE head_seen_at IS NULL OR head_seen_at < :mine`, and the same update stores `:mine`. That's a fencing token: without it, a slow job that cloned an older commit could finish last and roll the repo back. The loser's snapshot is kept, just not current.

**Q: Why the database clock and not `datetime.now()` in the worker?**
Workers can run on different machines with skewed clocks, and a skew of a few seconds could order two jobs wrong. One Postgres gives every worker the same clock. `clock_timestamp()` and not `now()`, because `now()` is the start of the transaction.

**Q: How do you stop the same commit being indexed twice?**
Three layers. The API reads HEAD with `git ls-remote` and keys the dedup marker on `url:sha`, so the same commit is queued once. If HEAD is already the current commit, the API queues nothing at all. And if a job runs anyway (redelivery), the worker finds the snapshot built after cloning and runs no agents; it only moves the pointer.

**Q: Why does the dedup marker never need freeing?**
It names a commit, and a commit's snapshot is built once. A new commit gets a new key, which is what lets a re-index through. The old URL-only key would have blocked every re-index forever.

**Q: What happens to a deep dive on a node from an old snapshot?**
Nothing breaks. The deep dive row points at its snapshot, and the worker clones that snapshot's commit, not the repo's current one. The node's paths were checked against that commit, so they still exist there. The list marks it stale: `deep_dive.snapshot_id != repo.current_snapshot_id`.

**Q: How did the migration move existing data?**
Autogenerate gave the schema changes; it can't move data. I added the columns as nullable, made one snapshot per indexed repo from its `commit_sha`, pointed the repo, its nodes and its deep dives at it, then set NOT NULL and dropped the old columns. The downgrade keeps each repo's current snapshot and deletes the rest, since the old schema holds one tree per repo. I ran both directions on the test database with seeded rows.

**Q: What's the known gap?**
If HEAD goes back to a commit that was queued before (a force-push revert), its dedup marker still exists, so nothing is queued and the pointer stays on the newer commit. The client gives up after its poll limit. The fix is to move the pointer in the API when that snapshot already exists. Old snapshots are also never deleted; collecting the ones no deep dive uses is a TODO.
